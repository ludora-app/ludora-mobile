# Ludora native builds & upgrades

## How builds run

- `bun ios` / `bun android` = `bash tools/vault/inject-env.sh expo run:<platform>` — env vars come from HashiCorp Vault via envconsul. Vault/auth failures are not build failures; ask the user to run the command if credentials are missing.
- `ios/` is generated by `expo prebuild` (CNG) and is not the source of truth — native config lives in `app.config.ts`, `app.json`, `plugins/` and `expo-build-properties`. Never hand-edit `ios/`; change config and prebuild.
- EAS profiles in `eas.json`; local EAS builds via `bun build:<platform>:<profile>:local`.
- Firebase config files: `dev.GoogleService-Info.plist`, `dev.google-services.json` (copied from EAS secrets in `eas-build-pre-install`).

## Debugging a failed build

1. Find the first `❌` in the xcodebuild output — ignore the "ambiguous dependencies" script warnings (pre-existing, harmless).
2. Identify the package from the path (`node_modules/<pkg>/...`) and check whether its version changed: `git diff bun.lock | grep <pkg>`.
3. Check toolchain vs requirements: `xcodebuild -version`, `swift --version`. Expo publishes the min Xcode per SDK at https://docs.expo.dev/versions/latest/ (SDK 57 → Xcode 26.4+, iOS 16.4+).
4. Search `github.com/expo/expo` issues/PRs for the exact error text before patching.
5. Clean retry: `rm -rf ios ~/Library/Developer/Xcode/DerivedData/LudoraDev-*` then `bun ios`.

## Upgrading Expo / RN

- `bun install:check` / `bun install:fix` (expo install --check/--fix) and `bun doctor` — use Expo-pinned versions, not `bun update`.
- After an upgrade, check `patchedDependencies` in `package.json`: patches are pinned to an exact version (`pkg@x.y.z`) and silently stop applying when the version bumps. Verify whether the upstream fix landed; drop or re-create the patch.
- Read the SDK changelog (https://expo.dev/changelog) for required Xcode and new native requirements (e.g. iOS 27 SDK scene lifecycle → `ios.enableSceneSupport`, default in SDK 58).

## Patching a dependency (bun patch)

```
bun patch <pkg>@<version>          # makes node_modules/<pkg> editable
# edit files in node_modules/<pkg>
bun patch --commit node_modules/<pkg>
```

This writes `patches/<pkg>@<version>.patch` and a `patchedDependencies` entry in `package.json` + `bun.lock`. To remove a patch: delete the file, remove the entry from `package.json` (watch the trailing comma), run `bun install`. Prefer a toolchain upgrade over a patch when upstream says so; always mention to the user when a patch should be removed later.
